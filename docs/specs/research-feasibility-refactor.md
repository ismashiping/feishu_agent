# 科研可行性与技术路线系统重构 SPEC

日期：2026-10-30。状态：整体方案与验收设计；未实现，未验收。用户本轮重新明确产品定位，按项目单任务约定先冻结设计，不一次实现整个项目。旧失败记录及医学未签署状态保留。

## 1. 需求与目标

从研究想法输出可追溯的已有工作判断、技术路线、关键瓶颈、候选机会和可验证的最小实验。系统支持定义、原论文解释、方法比较作为科研调研的辅助任务；方向评估是主流程。输出不是论文列表，也不承诺证明世界范围内不存在相关研究或证明创新性。

成功标准：研究者能看懂已有工作与自己想法的关系、复现路线的必要条件、哪些结论证据充分、下一步应验证什么。没有证据时输出调查缺口和待验证问题；不得编造“没人做”的原因。

## 2. 源码事实与复用边界

- src/feishu/worker.py：普通文本调用answer，只有/report调用report。自然语言方向问题没有自动进入报告路径。
- application/research.py：已有单一LangGraph及plan/retrieve/analyze/prior_art/design/report节点和共享期限、有界反馈，可继续复用。
- application/agents.py：现有角色分工可复用，不增加第二套多Agent编排。
- domain/report.py：已有事实/推断/假设、证据指针、支持度、八部分报告；render_report在默认输出暴露结构化计划、检索JSON、hash和chunk等审计细节，需要提供面向研究者的默认展示。
- OpenAlex、OA全文、E5、pgvector、事务、引用核验和飞书幂等/资源限制保留。既有契约变更须明确迁移，不重置数据。

## 3. 输入输出与数据模型（拟议，非当前实现）

输入继续使用QuestionRequest及request_id；在现有QueryPlan上定义任务意图：方向评估、方法比较、论文解释、概念定义。复用同一次规划结果驱动路由，不能先规划后重新调用report再次规划。显式/report保留。API/CLI原显式接口保留契约，飞书自然语言使用统一任务入口。

方向评估的结构化研究需求包含：研究对象、目标任务、关键方法、已知数据和资源约束、待澄清项。缺少可选资源条件不阻断检索；会改变检索对象的歧义才澄清。

复用AnalysisResult/ResearchReport/ReportClaim/EvidencePointer扩展表达，字段详细定义在各实现任务开始前冻结：

1. 已有工作：直接相关、部分相关/可迁移、未找到直接证据；给出检索范围和相似/不同点。
2. 技术路线：每项研究的输入、算法、数据、实验协议、指标、局限；原文未报告的字段标未知。
3. 瓶颈：论文明确报告的问题与系统推测分开；推测列依据、反证条件和验证方法。
4. 可行性：数据可得性、标注、方法适配、算力/实验条件，未知条件列为待确认，不给无依据的总分。
5. 候选机会：对应已有工作局限、区别、最小实验、基线、评价指标及失败判据；不使用“首次”“无人研究”作为默认结论。

默认报告面向人阅读，引用可点击且注明实际摘要/全文证据；完整原始对象留在审计输出。保留支持度不足和身份核验失败的发布门禁。

## 4. 执行流程

自然语言 → 单次需求规划 → 必要澄清或任务路由 → 有界证据发现 → 来源去重与相关性审查 → 按需合法全文 → 对应任务分析 → 引用/支持度核验 → 飞书可读回复。

方向评估复用analyze/prior_art/design/report；定义/论文解释/比较保留轻量回答路径。检索由问题拆解生成直接工作、相关方法与技术瓶颈等查询；各查询共享当前总预算，具体分配在检索任务冻结，不无限扩展搜索。

论文解释优先识别原方法身份，不能用下游应用代替原文。比较题允许两侧方法原论文分别支持机制，但不能冒充同条件性能对比。用户未限定近期的经典方法问题不强加最近年份约束。

## 5. 必要异常

记录安全request_id与既有错误码，禁止异常原文/密钥/用户问题写入常规日志。模型schema失败保持失败，先取字段诊断再修复，不截断造成功。超时、认证、限流、无证据、论文身份不明、全文不可用分别保留明确语义；缺全文可给摘要范围回答，缺证据不可生成有引用的虚假结论。未知异常在现有入口记录失败并清理资源。
