# 从入口到可靠交付

## 是什么

`channels/feishu` 是飞书消息接入边界。它把官方 SDK 事件转换为项目消息信封，经过容量控制和 Redis 幂等租约调用 `ResearchService`，再由独立发送线程交付结果。

五个模块各有独立职责：

- `events.py`：校验和过滤外部事件。
- `dedup.py`：用 Redis Lua 原子管理短期所有权和完成标记。
- `worker.py`：限制并发、调用研究服务并移交发送任务。
- `sender.py`：渲染结果、限制发送队列并调用官方 HTTP API。
- `main.py`：读取配置、组装资源、运行 SDK 和按顺序关闭资源。

## 为什么不能合成一个文件

接收回调必须快速返回，科研处理可能耗时，发送结果又具有“请求超时但服务端可能已接收”的未知状态。把它们写进同一个同步函数会混淆容量、所有权和重试语义。独立模块让事件准入、工作执行和最终交付各自保持可测试契约。

## 底层原理

同一条消息的稳定身份是 `(app_id, message|event, id)`。`events.py` 由该身份生成稳定 UUID；`dedup.py` 将身份哈希为 Redis key。Lua 脚本把读取、owner 校验和状态修改放在 Redis 单次原子执行中，避免两个进程同时处理。

工作线程只有拿到租约后才调用科研服务。发送前再次检查 owner；只有明确发送成功后才标记 completed。网络超时可能表示请求未到达，也可能表示飞书已接收，因此代码保留 `unknown`，不盲目重试造成重复消息。

## 最小 Demo

`demo.py` 构造一条点对点文本事件，调用真实 `filter_event`，展示 accepted、清洗后的文本和稳定 request_id；随后验证旧 `feishu.events` 与新模块是同一个对象。Demo 不创建任何外部资源。

## 工程取舍

旧包不是第二套实现。兼容文件通过 `sys.modules` 把旧模块名绑定到 canonical 模块，保证历史测试对模块全局的 monkeypatch 仍可见。控制台命令已切到新路径，而 Compose 暂留旧入口验证兼容；删除旧入口属于 Phase 5，必须先证明没有调用方。
