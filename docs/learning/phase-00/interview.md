# Phase 0 面试表达

历史范围：本文记录Phase 0对应任务/教材时点，旧测试数、模块数及“下一任务”不表示当前状态。当前进度见[任务表](../../development-plan.md#phase-1-任务进度)；在当前仓库跑全量测试须安装ml/db/rag/api四个extras，基础doctor示例仍无需这些业务依赖。

先讲做成了什么，再讲一个可验证的边界和取舍。以下以当前真实代码为准；医学 RAG/飞书/PubMed 属于后续阶段，不能描述为已经上线。

## 30 秒口述

“我先为医学文献 Agent 完成了可安装、可测试的 Python 工程骨架：用 uv 锁定依赖，Pydantic 做显式配置，structlog 输出受控 JSON 日志，CLI 和 runtime 分离。按 SPEC 逐项保留真实 RED/GREEN；当前 59 个测试覆盖配置、导入副作用、日志和入口生命周期。我还从新环境和独立 wheel 验证安装来源。当前完成的是 Windows 本地骨架，医学检索和真实服务将按后续阶段实现。”

## 1. 为什么先做 Phase 0，不直接接大模型

先固定可运行环境、配置与测试边界，后续模型或数据库失败时才能判断问题来自业务还是环境。当前工程没有为未来功能预建空 Service/Repository 层，只保留有实际用途的六个模块。

追问：这是否影响业务进度？答：范围被限制为可安装包、两字段配置、日志和 doctor，不同时实现 Phase 1–9；下一步先定义文献/证据 DTO，使来源和定位约束有测试依据。

## 2. 显式配置和依赖注入分别解决什么

load_settings 显式读取当前环境，避免 import 时读取/缓存。open_runtime 可直接采用注入 Settings；main 可采用注入的上下文工厂。前者控制配置何时产生，后者控制依赖由谁提供。它们配合使 help 无服务依赖、测试能固定关联 ID 和失败位置。

追问：为什么没有依赖注入框架？答：当前只需简单参数和 callable，框架不会改善当前边界，反而增加学习和测试成本。

## 3. 怎样保证成功结果可信

doctor 在 with 内构造报告，离开上下文成功后才发布 JSON；退出失败返回 1，不出现成功报告。装配阶段 ValidationError 返回 2，body/退出阶段同类异常返回 1，不能只按异常类型统一分类。[生命周期测试](../../../tests/unit/test_bootstrap.py) 在 finally 中检查 stdout 仍空。

追问：contextmanager 就自动保证所有资源关闭吗？答：它提供明确的进入/退出边界；实际资源仍需正确关闭逻辑。当前 Runtime 没有外部资源，不编造连接关闭能力。

## 4. 日志脱敏是否能保证任何秘密都不泄漏

当前保证是本模块 JSON handler 的字段控制：丢弃未知字段、非字符串上下文及原始异常/堆栈，标准日志不做位置参数文本插值。允许字段必须放受控值；不能把秘密写到 event/request_id 再期待系统识别。用户额外加的 handler 需要另行管理。

追问：为什么重复配置不会重复输出？答：只替换同名自有 handler，并关闭向 root 的传播；相关测试也确认不破坏其他 logger 的 handler。

## 5. 你如何证明做过 TDD

不是只展示最终绿色截图。P0-07a 的缺包测试先失败；配置、日志、runtime、CLI 也分别先观察目标缺失导致的失败，再最小实现。命令、退出码、计数与原始日志在 [开发计划](../../development-plan.md) 留存。配置测试曾误把 information 中的 info 子串判为泄漏，修正为完整 token 匹配，保留全部边界并如实记录首次失败尝试。

追问：为什么 P0-07e/P0-08 没有新 RED？答：它们是环境/文档和独立验收，没有新产品功能；人为破坏现有代码制造红灯没有验证价值，发现真实缺陷才补重现测试。

## 6. 59 个测试通过，是否等于所有功能完成

这些测试只证明 Phase 0 的配置、日志、装配和安装入口行为。Fake 验证 CLI 的上下文契约，不验证数据库、模型或飞书；真实 structlog 的本地集成也不等于医疗问答正确性。后续阶段必须有对应服务和证据的真实验收。

追问：覆盖率多少？答：P0-07e 父进程汇总 78%，语句 81%、分支 50%，未采集隔离子进程；日志主体/模块入口主要在那里执行。指标要解释测量范围，不能为凑比例删除边界或宣称全部路径已覆盖。

## 7. editable 和 wheel 的验证为何分开

editable 使开发导入指向 src，方便修改；wheel 必须证明打包后的文件能独立安装。P0-07e 用新开发环境重建 25 包，再用只含运行依赖的独立环境装 wheel，从临时 cwd 检查六模块来自 site-packages。检查 payload/RECORD/依赖/脚本与哈希，避免误把旧产物或源码路径当成安装成功。

追问：离线安装是否表示任意机器都能安装？答：这里只证明 Windows 及已有缓存；Linux、无缓存下载和具体外部服务仍需验证。wheel 的 py3-none-any 标签不代替其他平台运行证据。

## 8. 下一阶段如何保留医学证据可信性

先做 P1-01 的文献/证据 DTO 和来源/定位契约：未知 DOI/PMID 保持未知，日期保留精度，摘要和全文范围分开，每个证据块能回指来源。这是下一任务的计划，不是当前已存在的模型或问答接口；实际规则仍需细化 SPEC 后写失败测试。

## 练习说法

用一个真实场景回答“遇到了什么边界 → 如何测试 → 最小实现是什么 → 证据和局限是什么”。例如清理失败不得发成功报告，比背出使用了多少框架更能说明工程判断。每个结论最好能指到实际源码、测试或验收记录。
