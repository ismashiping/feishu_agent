# AI 开发规则

## 1. 项目开发模式

本项目必须遵循：

SPEC → TDD → 实现 → 测试验收 → 学习文档 → 阶段总结

每次仅开发当前阶段的一个任务，不允许一次性实现整个项目。

## 2. SPEC 规则

开发任何功能之前，先检查相应的 SPEC。

SPEC 必须包含：

- 需求与目标
- 功能边界
- 输入输出
- 数据模型
- 异常处理
- 测试场景
- 验收标准

如果 SPEC 不完整，先补充 SPEC。

## 3. TDD 规则

每个任务必须遵循：

1. 编写测试。
2. 运行测试，确认因缺少功能而失败（RED）。
3. 编写最小实现。
4. 运行测试并通过（GREEN）。
5. 必要时重构。
6. 运行回归测试。

禁止跳过测试，禁止虚构测试结果。

## 4. 技术原则

优先采用成熟、维护活跃且经过兼容性验证的工具。

技术候选包括：

- Python
- FastAPI
- Pydantic
- LangGraph
- PostgreSQL + pgvector
- SQLAlchemy + Alembic
- Redis
- sentence-transformers
- PyMuPDF
- lark-oapi
- Biopython Entrez
- pytest
- Docker Compose
- uv

不必一次引入所有工具。

避免重复造轮子、过度设计和没有必要的多 Agent 架构。

## 5. 阶段学习文档规则

每当一个 Phase 通过开发验收后，必须生成对应学习文档。

保存位置：

docs/learning/phase-XX/

学习文档必须面向没有接触过当前技术的初学者。

讲解顺序：

是什么 → 为什么需要 → 底层原理 → 最小 Demo → 项目真实代码 → 执行流程 → 调试测试 → 修改练习 → 面试表达

至少包含：

- README.md：学习导航
- tutorial.md：从零学习技术原理
- code-walkthrough.md：真实代码逐步解析
- exercises.md：练习与测试
- interview.md：面试题和口述答案
- troubleshooting.md：运行与排错

解释代码时必须按照实际执行顺序，说明关键函数、输入输出、资源生命周期、异常处理及设计原因。

所有教程必须基于真实代码，不允许编造函数、接口或测试结果。

每个阶段必须提供：

- 可运行的最小 Demo
- 实际项目执行流程图
- 关键代码解析
- 测试与调试方法
- 代码修改练习
- 独立实现练习
- 面试问题与 30 秒口述回答

没有学习文档，不允许标记阶段完成。

## 6. 开发过程输出

每完成一个任务，报告：

- 实现的功能
- 修改的文件
- 运行的测试和结果
- 尚未完成的问题
- 下一个任务

每完成一个阶段，报告：

- 阶段验收情况
- 学习文档位置
- 新增知识点
- 下一阶段规划

## 7. 开发边界

不得擅自扩大范围。

先完成可运行的最小功能，再逐步扩展。

异常处理等必须

外部 API、数据库和模型调用必须能进行隔离测试。

项目涉及医学文献引用时，必须保留可追溯来源，禁止编造 PMID、DOI 和研究结论。

未完成在线实时检索时，不得声称回答覆盖最新医学研究。

## 8. 任务停止规则

每次只完成用户明确指定的阶段或任务。

完成后停止，等待用户提出下一项开发任务。

不得自动进入下一个阶段。

# 工程化程度控制原则

本项目定位为具有实际工程能力的 AI Agent / 医学 RAG 简历项目。

采用“适度工程化”原则：

**核心业务完整、关键质量保障到位、非核心基础设施保持简单。**

## 必须具备

1. 清晰的模块划分和调用关系。
2. 使用成熟 SDK、框架与数据库。
3. 使用环境变量管理配置和密钥。
4. 使用锁定版本的依赖管理。
5. 使用数据库迁移管理 Schema。
6. 使用 Docker Compose 实现可复现部署。
7. 使用 pytest 测试核心业务和关键边界。
8. 在外部系统边界设置超时及必要的异常处理。
9. 保证文献入库与飞书消息处理的基本幂等性。
10. 保证异步任务不会无限制占用资源。
11. 使用简单日志辅助定位问题。
12. 使用 Pydantic、类型标注和 Ruff 保证基础代码质量。
13. 保证医学引用能够追溯至真实来源。

## 不需要实现

- 复杂的自定义异常继承体系
- 多层 Repository / Service / Factory 抽象
- Kubernetes 和微服务
- 分布式事务
- 完整可观测性平台
- 复杂熔断与补偿框架
- 过度通用的重试系统
- 大量与核心业务无关的单元测试
- 没有实际性能需求的提前优化

## 代码质量要求

尽量减少样板代码，但不得牺牲核心业务正确性、数据一致性和基本可测试性。

优先选择简单、明确、可运行、可解释的实现。

一个工程机制只有满足以下至少一项才值得增加：

- 解决真实存在的业务问题
- 避免重要的正确性或数据一致性问题
- 明显提高代码可维护性
- 有助于测试核心业务
- 能够展示与目标岗位相关的工程能力

不允许仅为了显得专业而增加复杂设计。

每个阶段采用 SPEC → TDD → 验收 → 学习文档 的流程，并且学习文档需解释本阶段关键的工程设计取舍。
