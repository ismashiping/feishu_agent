# Phase 0 修改练习与独立实现

历史范围：本文记录Phase 0对应任务/教材时点，旧测试数、模块数及“下一任务”不表示当前状态。当前进度见[任务表](../../development-plan.md#phase-1-任务进度)；在当前仓库跑全量测试须安装ml/db/rag/api四个extras，基础doctor示例仍无需这些业务依赖。

以下均为读者作业，未在当前产品实施，不计入 59 个既有测试。先完成 [教程](tutorial.md) 和 [代码解析](code-walkthrough.md)。在自己新建的练习目录或副本中动手，保留现有测试；不要改共享 Conda，也不要把练习输出提交为医学业务实现。

## 1. 阅读练习：先预测，再证明

分别预测以下行为，并指出真实函数和已有测试：

| 输入/操作 | 你应说明什么 |
| --- | --- |
| LOG_LEVEL 为非法字符串，执行 --help | 为什么不构造 Settings，退出码和输出通道是什么 |
| 相同非法环境执行 doctor | 为什么返回 2，为什么不能直接打印 ValidationError.errors() |
| INFO 改成 WARNING 后 doctor | stdout 是否仍有报告，stderr 的 INFO 事件是否存在 |
| 明确传入 Settings，同时主机环境冲突 | open_runtime 是否重新读取环境 |
| 报告构造成功但上下文退出失败 | 为什么不能预先 print 成功结果 |
| 向 token/payload 字段写入假秘密 | 哪个筛选函数丢弃它；允许字段里放秘密是否同样保证 |
| 从临时目录运行已安装 wheel | 哪个路径检查能区分 wheel 与 editable |

验收：每项写出预测、源码位置和可验证证据；不能用“因为测试通过”代替说明。对照 [排错手册](troubleshooting.md) 的测试命令验证预测。

## 2. 修改练习：只在副本新增 --version

目标：体会如何增加小功能而不破坏 help 和装配边界。这不是当前 CLI 已支持的选项，也不是授权修改正式阶段范围。

先写练习 SPEC：`clinical-agent --version` 和 `python -m clinical_agent --version` 各输出 `clinical-literature-agent 0.1.0` 加换行到 stdout，stderr 空，退出 0；非法环境也不构建 runtime。使用安装元数据取得版本，不复制硬编码项目版本，不新增依赖。仅主命令支持此选项，不默认增加 doctor --version。

测试清单先于实现：

1. 注入调用即失败的工厂，--version 仍成功，证明未装配。
2. 模块和已安装脚本入口均输出同一发行版本；不要只测直接函数调用。
3. 非法环境配置不影响版本输出，不能捕获异常后假装成功。
4. 既有无参数/help/doctor/安全错误用例仍通过。

先跑新增测试并保存缺少选项造成的失败；再使用 argparse 的成熟版本动作等最小机制完成；最后运行相关回归和 Ruff/mypy。如果修改了安装元数据或脚本声明，重新安装副本并核对来源，不得误测正式项目。

验收材料：一页 SPEC、RED 原始命令/失败原因、GREEN 原命令、实际变更、回归结果。不要删旧断言来使计数变绿；没有运行就写“未运行”，不能照抄本项目历史结果。

## 3. 故障练习：辨认阶段，而不是统一吞错

不改产品，可在现有 [生命周期测试](../../../tests/unit/test_bootstrap.py) 中阅读 Fake 工厂，画出三条时序：进入前配置验证失败、body 验证失败、退出验证失败。

在练习副本补一个断言或新场景前，先解释它验证了哪个已有断言未覆盖的真实风险。若确有缺陷，补重现 RED 后修复；不要仅为数量添加镜像测试。预期始终是：进入前配置错误返回 2；body/退出异常返回 1；失败不发布成功 JSON；已进入就执行退出动作。

验收：能解释 entered 标记为何必要，为什么在 with 内 print 会破坏失败结果，为什么 Fake finally 通过不表示真实 SDK 资源已关闭。

## 4. 独立实现：一个本地 lab-status 命令

在新的练习目录独立编写一个单文件程序，不导入 clinical_agent，也不复制项目源码。可以复用标准 argparse/contextlib、已安装 Pydantic；不要重写环境解析库、日志框架或依赖管理器。

先冻结自己的输入输出，再写测试。最低契约：

- 命令为 help/status，status 只生成本地环境信息，不联网、不操作用户数据。
- 配置含 app_env，默认 development，合法 development/test；明确读取时机与 .env 策略。
- 接受 callable 上下文工厂，成功进入后提供配置与关联 ID；默认生成 UUID，测试可注入固定值。
- stdout 只返回 status/app_env/request_id；stderr 只放固定安全错误。先成功退出上下文再发布结果。
- help 不装配；配置失败与 body/退出失败用不同退出码；错误中的固定假秘密不得进入结果。

最小验收用例：help + 坏环境、默认 status、固定 ID 注入、进入配置错误、body 异常、退出异常。每个行为完成真实 RED/GREEN，按需组合参数化；不要求写框架或达到某个覆盖率百分比。

评分关注：接口清楚、可运行、错误阶段正确、依赖可替换、输出可解析、过程有真实证据。资源只在真实存在时关闭，不用空 close 方法装饰代码。这里的 lab-status 是练习程序，不添加到正式项目 CLI。

回答三个问题：哪些测试证明对外行为，哪些只是安装/来源检查；当测试失败时如何确认是产品缺陷还是测试误判；如果要接数据库，哪些当前证据仍有效、哪些必须新增真实集成验证。
